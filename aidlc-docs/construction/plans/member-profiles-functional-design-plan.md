# Functional Design Plan — Unit 3: Member Profiles & Directory

**Stage**: CONSTRUCTION → Functional Design · **Unit**: Member Profiles & Directory (8 stories, revised 2026-08-02)
**Contract (frozen, to be amended)**: `contracts/services/member-profiles/openapi.yaml` · **Permission spec**: `contracts/platform/permissions/role-permission-matrix.v1.json`

## Scope (revised 2026-08-02 after UI-mockup cross-check — see Amendments below)
Stories US-3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 3.10 (8). Paths `/members`, `/members/me`, `/members/{id}`, `/members/{id}/activity`. Owns the Member-profile table (denormalized, event-sourced cache). Publishes `MemberProfileUpserted`. Consumes `UserProvisioned`, `UserRoleChanged`, `UserDeactivated`, `MemberJoinedGroup`, `MemberLeftGroup`, `MemberRemoved` from Identity & Access. Delegates semantic search (US-3.5) to the shared Search service (conditional, `EnableSemanticSearch`), degrading to keyword/attribute filtering when disabled. **US-3.8/US-3.9 (admin member list/export) are reassigned to Unit 2 Identity & Access** — no longer in this unit's scope (see Amendment 3).

## Amendments (2026-08-02, from UI-mockup cross-check — user-requested "did you refer the UI mock?")
Original Q1–Q9 below were resolved from unit-of-work.md/story-map/use-case/contract/fixtures/dependency-matrix, but **without checking `requirements/mockup/`**. Cross-checking against `member/profile.html`, `member/view-profile.html`, `member/directory.html`, `leader/directory.html`, `admin/users.html`, `assets/exports.js`, and the already-shipped frontend (`AdminUsersPage.tsx`, `MemberDetailPage.tsx`, `singletons.tsx`) surfaced 3 corrections:

1. **Activity summary is two-tiered (supersedes original Q2's single-endpoint framing).** A basic 4-stat block (events attended, forum posts, contributions, certifications — **no points**) is inline on **every** profile view — own (US-3.1) and read-only other (US-3.3) — visible to any role that can view a profile. The leader-only, points+lifetime+date-range-filtered version is the distinct **US-3.10** (`memberActivity`): CL any member, UGL own-group-only, Administrator and self-view excluded. `getOwnProfile`/`getMember` return the basic block inline (still via the Q2 REST fan-out to Events/Forums/Contributions/Certifications, degrading per-section on failure); `memberActivity` is the separate detailed drill-down with `range` query params.
2. **Admin member list/export reassigned to Unit 2 (was Q6; user confirmed via DynamoDB check).** `admin/users.html` mockup and the shipped `AdminUsersPage.tsx` both call Identity & Access's `GET /users`, not `/admin/members`. Confirmed by inspecting both data stacks: `identity-access-<stage>` is a real, deployed single-table with GSI1(email)/GSI2(role)/GSI3(group-history) already holding every US-3.8/3.9 field (city/country/professionalRole/awsProject/status/groups); `member-profiles-<stage>` is a bare pk/sk table still on the mock handler with no indexes. Building a real `/admin/members` would duplicate Identity's already-indexed data with sync lag for zero benefit, and would require reworking a page that already works. **US-3.8/US-3.9 moved to Unit 2 Identity & Access** (unit-of-work.md, story-map, dependency-matrix updated). Member Profiles' functional design no longer covers them.
3. **CSV export scope narrowed (supersedes original Q8).** The points/tier-bearing CSV in `leader/directory.html`'s "Export Member Data" modal (join-date range, `current_quarter_points`/`current_tier` columns, `MEMBER_HEADER` in exports.js) is **US-7.10**, owned by Unit 8 Analytics per the story-map's cross-unit note ("US-7.10 | Export members | 3, S3"). It is out of scope for Unit 3 entirely (no points data ever flows through this service). Since US-3.9 (identity-only export) is now also out of scope (moved to Unit 2, per Amendment 2), **this unit ships no CSV export.**

## Questions analysis → resolved from existing artifacts (no blocking questions)

| # | Area | Resolution source | Decision |
|---|---|---|---|
| Q1 | Profile record provisioning — does Member Profiles JIT-create its own row, or rely on Identity's record? | Unit-of-work.md ("Owns: Member-profile table"); consumes `UserProvisioned`/`UserRoleChanged`/`UserDeactivated` | Member Profiles owns a **separate, denormalized profile-extension record** keyed by the same user id (Cognito `sub`). It is created/updated **only** by consuming Identity's events (`UserProvisioned` → create; `UserRoleChanged`/`UserDeactivated` → sync role/status) plus the member's own edits (`updateOwnProfile`). It never calls Identity synchronously — event-driven alignment only (per FQ2, async is default; matches "Consumes: UserProvisioned, UserRoleChanged, UserDeactivated (align profile records)"). |
| Q2 | Cross-service reads for rollup/tier (US-3.1/3.3) and activity summary (US-3.10) — sync REST or precomputed projection? | component-methods.md ("ActivitySummaryAssembler reads activity via events/other services"); dependency matrix doesn't list Contributions/Events/Forums/Certifications as Unit-3 runtime deps, but FQ2 allows sync REST for read-time lookups | **Sync REST fan-out at read time** (not a materialized projection). `getOwnProfile`/`getMember` call Contributions & Scoring for the display-only current-quarter rollup + per-group tier, **plus** a lightweight basic-activity-count fan-out to Events/Forums/Contributions/Certifications for the inline 4-stat block (see Amendment 1 — mockup shows this on every profile view, not just leader-facing). `memberActivity` (US-3.10, leader-only) does the fuller fan-out with points + lifetime totals + date-range filter. Each call independently try/caught — a downstream outage degrades that section (empty/blank), never fails the whole response. **Resolved**: `unit-of-work-dependency.md` updated (2026-08-02) to add "3 Member Profiles → 4 Events, 5 Forums, 6 Certifications, 7 Contributions (REST, read-time)". |
| Q3 | Onboarding (US-3.6) and Welcome notification (US-3.7) — owned by this service or thin/UI-only? | gap-analysis.md ("US-3.6/3.7 — behavior described in the member dashboard but no standalone screen. Low risk"); groups live in Identity & Access | Member Profiles owns **no new endpoints** for these two stories. Onboarding (US-3.6) is a **frontend orchestration** over Identity's existing `GET /groups` + `POST /groups/{id}/join` (shown once, gated on the profile record being newly created — i.e., `createdAt` recent / no prior groups). Welcome notification (US-3.7) is triggered off `UserProvisioned` by the **Notifications** service (Unit 10), not by Member Profiles. This matches the unit's "no exclusively-owned stories requiring new API shape" characteristic for these two. |
| Q4 | Semantic search (US-3.5) integration — who calls OpenSearch/Search, and what is the degrade path? | contracts/services/search/openapi.yaml (`GET /search?kind=member&q=`); unit-of-work.md ("delegates search to Search"); D3 Conditions gate Search | Directory search is served by **`browseDirectory` with a `q` query param** (own contract path, not `/search` directly exposed to the SPA — mirrors Forums' pattern of a dedicated `/forums/search` op, so Member Profiles gets its own `x-semantic-search` op too — **flagging a contract gap**: the frozen `member-profiles/openapi.yaml` has no dedicated search operation or `q`/`role`/`groupId`/`certId` filter params on `/members`). Resolution for this build: extend `browseDirectory` (`GET /members`) with optional query params `q`, `role`, `groupId`, `certId` (US-3.5 filters; `certId` omitted for the Community-Leader-facing directory per US-3.5's CL-omits-cert-filter rule, enforced by role in the handler, not by a separate endpoint). When `EnableSemanticSearch` is on, `q` delegates to the shared Search service (`GET /search?kind=member&q=`); when off, `q` degrades to a case-insensitive substring match against name/email/skills in DynamoDB (keyword fallback, per D3 "consumers degrade gracefully"). |
| Q5 | Embedding generation trigger for search (US-3.5) | US-3.5 ("embeddings generated on profile create/update"); `MemberProfileUpserted` event; AI Gateway is conditional | Member Profiles publishes `MemberProfileUpserted` after every create/update (JIT-create from `UserProvisioned`, or `updateOwnProfile`/Edit-User-driven profile fields). The shared Search service (Unit 13) consumes this event and calls the AI Gateway (Unit 14) to generate the embedding — **Member Profiles never calls AI Gateway directly** (keeps this unit's blast radius small; matches unit-of-work.md "Consumed: MemberProfileUpserted" on Search's row, and AI Gateway's "invoked by 3,5,7,8,12,13" is read as "on Search's behalf for 3", not a direct call from 3). No member-profile hard-delete exists (Phase 1), so embeddings are never removed (BR-8, US-3.5). |
| Q6 | Admin member list (US-3.8) vs. Identity's `GET /users` — is this a duplicate source? | use case 03; identity-access `GET /users` already returns the same shape (role/status/groups) | **RESOLVED (was an open question, now answered — see Amendment 2).** US-3.8/US-3.9 reassigned to Unit 2 Identity & Access. `GET /users` (already shipped, already indexed via GSI2, already the frontend's/mockup's actual caller) serves both stories. Member Profiles builds **no** `/admin/members` endpoint and **no** admin-list functional design. |
| Q7 | Directory/profile visibility scoping by role | BR-R3 (Identity, Administrators don't participate in community activities); US-3.3 (Admins cannot view community profile) | `getMember` (public read-only profile) returns **403** for principal role `Administrator` (US-3.3 explicit exclusion; Admins use Identity's `/users` list instead — Amendment 2). `memberActivity` (US-3.10) is CL (any member) / UGL (own led group only, 403 if member outside group) — **403** for Administrator and for Member (self-view not offered by this story; a member's own basic activity counts appear inline on `getOwnProfile` per Amendment 1, not via this endpoint). |
| Q8 | Directory pagination + CSV export (US-3.4/3.9) | use case 03 ("pagination for large lists"); existing `exportEndpointCsv` frontend helper already targets `/members` | **Revised (see Amendment 3) — US-3.9 moved to Unit 2, no export in this unit.** `browseDirectory` still accepts `limit`/`cursor` (or `page`/`pageSize`) query params for pagination (US-3.4); response `{items, count}` unchanged for backward compatibility — minor backward-compatible contract addition (no `vN+1` needed). The frontend's existing `exportEndpointCsv("/members", ...)` call in `pages.tsx`'s `DirectoryPage` remains a plain member-directory export (identity fields only, no points) since `/members` itself has no points data — this is **not** the US-7.10 points-bearing export, which belongs to Analytics and is out of scope here entirely. |
| Q9 | Data model for per-group join dates shown on profile (US-3.1/3.3/3.4) | domain-entities.md E4 MembershipEvent (Identity, append-only, source of truth); Member Profiles owns no membership data | Member Profiles does **not** duplicate membership-event history. Per-group join dates + `memberGroupIds` are populated into the profile-extension record by consuming Identity's `MemberJoinedGroup`/`MemberLeftGroup`/`MemberRemoved` events (denormalized `groups: [{groupId, joinedAt}]` list), keeping this a **read-optimized cache**, not a second source of truth. Rejoin (same group, later `MemberJoinedGroup`) overwrites that group's `joinedAt` (BR-G5 semantics preserved). **Flagging**: this adds three more Identity events Member Profiles must consume beyond the three listed in unit-of-work.md (`UserProvisioned`/`UserRoleChanged`/`UserDeactivated`) — `MemberJoinedGroup`, `MemberLeftGroup`, `MemberRemoved` — needed to keep the directory's per-group-join-date column (US-3.4) correct. |
