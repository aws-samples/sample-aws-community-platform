# Business Rules — Unit 2: Identity & Access

**Stage**: CONSTRUCTION → Functional Design · **Unit**: Identity & Access
Enforceable rules distilled from use case 01 + Role-and-Permission-Mapping.md. Rule IDs are referenced by code and tests. Companions: `business-logic-model.md`, `domain-entities.md`.

## Authentication (A)
- **BR-A1** — Every user, including the bootstrap Administrator (US-1.27), authenticates with email + password against Cognito (US-1.2); there is no separate local credential path (US-1.27/1.28 tombstone).
- **BR-A2** — (Retired) Previously distinguished a portal-local `accountType`; removed when the bootstrap Administrator became an ordinary Cognito user (US-1.27). Rule ID retained as a tombstone; do not reuse.
- **BR-A3** — OTP re-verification is **due** when `now - lastVerifiedAt >= interval` (interval from Settings US-8.3). When due, login returns an OTP challenge (`otpRequired=true`) and a session is granted only after successful `verifyOtp`. When not due, password alone completes login.
- **BR-A4** — On successful OTP verification, set `lastVerifiedAt = now`. The local Administrator is exempt from OTP (US-1.32).
- **BR-A5** — OTP codes have short expiry and a capped attempt count; exceeding attempts invalidates the challenge (lockout). Rate-limit issuance (SECURITY-11/12).
- **BR-A10** — **Proven mailbox control sets `lastVerifiedAt` (added 2026-08-11, US-1.30/1.32).** Completing the Cognito forgot-password flow requires a code delivered to the registered address, which is the same assurance the in-service OTP obtains — so a successful `confirmResetPassword` stamps `lastVerifiedAt = now`. Consequence: under BR-P8 no account can be used before its mailbox is proven, so a **first-login** OTP is redundant on every path and is not issued. This does NOT weaken US-1.32: periodic re-verification still fires on its interval, and that is the control that detects a user who has since LOST mailbox access (a departed employee) — something first-login proof can never establish. Stamping is best-effort bookkeeping: it must never turn a completed password reset into an error, and its outcome must not vary the response (BR-A6).
- **BR-A6** — Auth failures (bad password, bad/expired OTP, unknown email) return a generic error and never reveal whether an account exists (no user enumeration — US-1.32). **Extended 2026-08-11**: this applies to **self-registration** too. An address that already has an account must return the same response as a new one (US-1.30) — a distinguishable error there discloses who holds an account just as effectively as a login probe.
- **BR-A7** — Logout invalidates the session; the client is redirected to login (US-1.3).
- **BR-A8** — (Retired) Previously exempted a portal-local Administrator from role-change/disable/sync. The bootstrap Administrator is now an ordinary Cognito user subject to the same rules as any other Administrator (US-1.27/1.33) — no exemption. Rule ID retained as a tombstone; do not reuse.
- **BR-A9** — Password reset (US-1.20) is the two-step Cognito hosted forgot-password flow (`resetPassword` requests a verification code; `confirmResetPassword` submits the code + new password) for every user, including the bootstrap Administrator — there is no portal-local reset path. Cognito enforces the password policy and code expiry/attempt limits. Both steps return generic responses/errors (no user enumeration, BR-A6). Every reset request and confirmation is audited (US-1.13).

## Provisioning & lifecycle (P)
- **BR-P1** — Portal records key on Cognito `sub` (email unique). JIT provisioning on first login is a **no-op if a record already exists** (US-1.15); default role = Member.
- **BR-P2** — Scheduled Cognito sync is **idempotent match-and-update** — never creates duplicates; the local Administrator is exempt (US-1.4).
- **BR-P3** — Self-registration is allowed only if the email domain is on the Settings allow-list; empty allow-list ⇒ registration blocked (default assumption) (US-1.30). Self-registration can grant only the Member role. **Amended 2026-08-11**: the master switch (`selfRegistrationEnabled`, US-8.3) fails **CLOSED** — when the live Settings value cannot be read, registration is treated as disabled. Hiding the sign-up tab in the SPA is presentation only; `/auth/register` is a public route and the server-side gate is the control.
- **BR-P4** — Bulk import: create each valid row in Cognito, then create the portal record at import time keyed to the returned `sub`, default role Member. Row outcomes: `Created` / `Skipped (duplicate)` / `Rejected (domain not allowed)` / `Rejected (invalid data)`. Within-file duplicate emails (case-insensitive) rejected; existing Cognito emails skipped. Never overwrites an existing account. The created Cognito account is set to a system-generated password as PERMANENT immediately (no Cognito invitation email, no `FORCE_CHANGE_PASSWORD` state) — the same `CONFIRMED` outcome as self-registration and the bootstrap Administrator. The generated password is never disclosed to anyone; the portal instead sends the new user a welcome email (via SES) directing them to "Forgot password" to set their own. Import is audited (US-1.31).
- **BR-P5** — Disable (US-1.33) disables the Cognito account and marks the portal user `Inactive`, triggering full deactivation handling (BR-P6). Enable re-enables Cognito and marks `Active` (US-1.19). Local admin cannot be disabled (BR-A8).
- **BR-P6** — Deactivation (US-1.6): user removed from all groups (append `left`/`removed` membership-end events), removed from future RSVP lists, pending contribution/certification submissions auto-rejected (via published `UserDeactivated`), content retained/attributed, excluded from leaderboards. Notify by email.
- **BR-P7** — Reactivation (US-1.19) restores the previous role and marks `Active`; group memberships are **not** auto-restored (user re-joins). User can log in immediately.
- **BR-P8** — **Unified account provisioning (added 2026-08-11, US-1.30/1.31).** EVERY provisioning path — self-registration, Administrator-created, bulk import — creates the Cognito identity the same way: a system-generated PERMANENT password that is never disclosed or emailed, and no Cognito invitation. The new user establishes their own password through "Forgot password" (US-1.20). Every path also creates the portal record **at provisioning time** (self-registration included, since 2026-08-11 — deferring it to JIT left nothing for BR-A10 to stamp and reintroduced the first-login OTP), publishes `UserProvisioned`, and leaves JIT as the BR-P1 no-op fallback. **No path may accept a caller-supplied password at creation time** — that is what makes mailbox control structural: the only route to a usable credential is reading a code sent to the registered address. `email_verified` IS set to `true` on every path and must remain so: Cognito refuses to deliver a forgot-password code to a user with no verified email, so unsetting it would leave the account with no reachable credential at all. The flag is a delivery precondition, NOT the source of assurance (corrected 2026-08-11 — see `us-1.30-unified-provisioning.md`). Paths differ only in **who initiates** (anonymous caller vs. authenticated Administrator), **which role** is assigned (self-registration: Member only, BR-P3), and **whether the domain allow-list gates it** (an empty allow-list blocks self-registration only, not Administrator-driven creation). No path may accept a caller-supplied password at creation time. Rationale: mailbox control is then proven structurally on every path, because no account is usable until a code sent to its address has been read — the lower-trust path (anonymous) must never carry weaker proof than the higher-trust one (admin-vouched).

## Roles & access control (R)
- **BR-R1** — A user holds exactly one role at a time; roles are mutually exclusive and have no inheritance (US-1.5/1.12).
- **BR-R2** — AuthZ is enforced in-service, fail-closed, from `role-permission-matrix.v1.json`: `global` (role suffices), `own` (principal owns the resource — IDOR guard), `group` (resource's group ∈ principal's led/member groups). Unauthorized ⇒ 403 with a user-friendly message (US-1.12, SECURITY-08).
- **BR-R3** — Administrators cannot participate in community activities (cannot create/join groups, RSVP, post). Community Leaders manage all groups without membership and earn no points. User Group Leaders are scoped strictly to the one group they lead. Members participate normally (US-1.12).
- **BR-R4** — Edit User (US-1.26) sets role + group membership + profile fields (city, country, professionalRole, awsProject, timeZone) in one action; identity fields (name, email) are read-only. Role change takes effect on next action (no re-login).
- **BR-R5** — Role-change data handling (suspend, not destroy): promotion to a non-Member role marks memberships inactive, keeps points/badges in ledger, auto-rejects in-flight submissions, removes from future RSVPs. Demotion to Member reactivates memberships and resumes earning from the current quarter. (Cross-unit effects delivered via `UserRoleChanged`.)

## Group membership rules by role (BR-R6, US-1.26)
- Administrator — cannot belong to groups.
- Community Leader — group membership not applicable.
- User Group Leader — leads exactly one group; belongs to no other group.
- Member — may belong to one or many groups.

## Groups (G)
- **BR-G1** — A group must have ≥1 User Group Leader at all times; creation requires assigning ≥1 leader; removing/relocating the last leader is blocked (US-1.7/1.9/1.10/1.18).
- **BR-G2** — Only Community Leaders create, edit (name/description/approval flag/leaders), and delete groups. User Group Leaders cannot edit group config. Administrators cannot create/edit/delete/join groups (US-1.7/1.18/1.11).
- **BR-G3** — Open group: join is immediate. Approval-required group: join creates a Pending JoinRequest; the user is not a member until approved (US-1.8).
- **BR-G4** — At most one Pending JoinRequest per (member, group); the requester may cancel their own pending request (US-1.8/1.21).
- **BR-G5** — Per-group join date = the membership-start event time: instant of join for open groups, instant of approval for approval-required groups. Rejoin resets the displayed join date (US-1.8).
- **BR-G6** — Approval-flag changes are not retroactive: existing members unaffected; outstanding pending requests remain pending; new setting applies only to future joins (US-1.18).
- **BR-G7** — A person can lead only one group; assigning a leader who already leads another group is rejected. Assigning the UGL role updates the user's role (US-1.10).
- **BR-G8** — Only a User Group Leader of the group **or** any Community Leader may approve/reject join requests; first actor wins; the request is removed from both queues. Approve → membership + email/in-portal notify; Reject → requires reason + notify (US-1.21).
- **BR-G9** — Delete is a soft-delete (2-week grace, restorable). On soft-delete: hide group + data, remove all members (membership-end events), auto-reject group-scoped pending submissions, cancel upcoming group events + notify RSVPs (via `GroupSoftDeleted`). Restore notifies former members. After 2 weeks: permanent delete + ledger purge + search-index removal (via `GroupHardDeleted`) (US-1.11).
- **BR-G10** — Group directory: Community Leaders see/manage all groups; User Group Leaders see all but manage only their led group; Administrators do not manage the directory (US-1.16). Group listings show each leader by name + email (US-1.8).
- **BR-G11** — Remove member (US-1.17): Community Leader from any group; User Group Leader from their led group only; append `removed` event; notify by email; member may rejoin later.
- **BR-G12** — Last-Community-Leader / last-User-Group-Leader safeguards: any change (role change, deactivation, leaver, removal) that would leave a group leaderless or the community with zero active Community Leaders is blocked or flagged (US-1.6/1.26/1.33).

## Membership history (M)
- **BR-M1** — Every membership change appends an immutable event (`joined`/`approved`/`left`/`removed`) with member, group, timestamp. Current membership + join date are derived (latest start with no later end). History is retained indefinitely except on group hard-delete, which purges that group's events (US-1.34).

## Audit (AU)
- **BR-AU1** — When audit logging is enabled, all create/delete/update operations and all logins/logouts are written to CloudWatch Logs with user ID, action type, timestamp, IP address. Retention 12 months (US-1.13).
- **BR-AU2** — Audit toggle (US-1.14): when off, no new entries; existing data preserved; the toggle change itself is always logged regardless of state.

## Events (EV)
- **BR-EV1** — State-changing operations publish the corresponding domain event (E7) wrapped in the platform envelope after the write succeeds; publication failures are logged and retried but never block the primary write's success response (best-effort, at-least-once; consumers are idempotent).

## Validation & errors (V)
- **BR-V1** — All inputs validated (type, length, format, email, enum) before processing; reject HTML/script in free-text (SECURITY-05). Bodies size-capped.
- **BR-V2** — Unimplemented contract operations return `501` until shipped (FQ8/BR-17 platform). All errors use the platform error shape with generic messages (SECURITY-15).
