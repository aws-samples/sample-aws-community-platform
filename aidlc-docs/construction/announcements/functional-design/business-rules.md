# Business Rules — Unit 9: Announcements

**Stage**: CONSTRUCTION → Functional Design · **Unit**: Announcements
Enforceable rules distilled from use case `10-announcements.md`, the frozen contract, the permission matrix, the UI-mockup sweep (2026-08-07), and the finalized functional-design decisions incl. two user-approved requirement deviations. Rule IDs are referenced by code and tests. Companions: `business-logic-model.md`, `domain-entities.md`, `frontend-components.md`.

## Authoring & authorization (1–4)
- **BR-1** — Only **Community Leaders** and **User Group Leaders** may create announcements (`create announcement` in `role-permission-matrix.v1.json`: CL scope `global`, UGL scope `group`). Members and Administrators cannot create → 403.
- **BR-2** — Targeting is role-bound (US-10.2): a **CL** may target `community` (all members + leaders) or one-or-more **selected groups**; a **UGL** may target **only the group they lead** — the server forces `target = {scope: groups, groupIds: [ledGroupId]}` from the caller's `ledGroupId` claim and ignores/rejects any other target in the request body (the UGL UI shows the audience as a read-only field). Group-targeted announcements are seen by all that group's members including its UGL(s).
- **BR-3** — **Administrators are excluded from the entire feature.** Every announcement operation (create, edit, delete, list/panel) returns 403 for role `Administrator` — they neither author nor receive community announcements (use case 10 Roles).
- **BR-4** — Edit is **author-only**. Delete is permitted to the **author**, and additionally to **any CL** for moderation (`delete announcement` CL scope `global`, UGL scope `own`). A UGL may delete only announcements they authored. A CL's global-delete right does **not** extend to editing another author's content.

## Expiry (5–6) — *requirement deviation, user-approved 2026-08-07*
- **BR-5** — Expiry is **mandatory**. On create/edit, if no `expiresAt` is supplied it defaults to **`now + 2 days`**; any supplied value is clamped to a maximum of **`now + 90 days`**. (Supersedes the original optional-expiry / "remains until deleted" clause — see US-10.1 deviation note. Rationale: enables TTL-based cleanup and a bounded read set.)
- **BR-6** — An announcement with `expiresAt <= now` is **never returned by any panel or `mine` panel query** and is not counted in the active-count badge; "removed from all views after expiry" is enforced at read time (authoritative), independent of the DynamoDB TTL sweep, which only reclaims storage and may lag. In the author's `view=mine` management list, an expired announcement still appears with a derived **Expired** status (US-10.3).

## Viewing panel (7–13)
- **BR-7** — Each announcement is a **single stored definition** (source of truth). There is no per-user copy and no write fan-out; posting/editing/deleting is one write regardless of audience size (US-10.4 performance basis).
- **BR-8** — Display fields shown in the panel — `authorName`, `authorRoleLabel` (e.g., "Community Leader"/"User Group Leader"), and `source` ("Community-wide" or the group name) — are **denormalized at create time** and stored on the item, so panel reads make **zero per-row cross-service calls**. Name/group-name resolution forwards the caller's JWT; if it fails, it falls back fail-closed to email/id / raw group id and the post still succeeds.
- **BR-9** — Posting an announcement does **not** create a bell/in-portal notification and is **not** a US-8.15 recipient-matrix trigger — it appears only in the announcement panel (US-10.1). Email is the only side channel, and only when opted in (BR-10).
- **BR-10** — Optional email is delegated: create publishes `AnnouncementPublished` carrying `emailOptIn` + resolved audience; **Notifications (Unit 10)** sends the email via the configured sender/templates. Announcements never calls SES directly. Email opt-in defaults **off** (US-10.1). Edits do not re-send email unless `emailOptIn` transitions off→on.
- **BR-11** — Dismissal is **client-side only** (browser `localStorage`); there is **no server dismiss endpoint and no Dismissals table** (*requirement deviation, user-approved 2026-08-07* — supersedes US-10.5's cross-device "remembered"). Dismissing hides the announcement from that member's own browser view; it never deletes it or affects other members or the author. Acceptable because BR-5 bounds an announcement's lifetime to a short, mandatory window.
- **BR-12** — The panel is **collapsed by default**, showing the active count in its header (e.g., "Announcements (3)"); it renders on the caller's landing page — Member Home for Members, the community analytics dashboard for CLs, the group analytics dashboard for UGLs (US-10.4). A CL's panel shows community-wide announcements plus group-targeted ones **they authored**; a UGL's shows community-wide plus their led group's.
- **BR-13** — When a group is soft-deleted, its group-targeted announcements are hidden from all views: Announcements consumes `GroupSoftDeleted` and sets `groupHidden = true` (excluded by BR-6-style read filtering); it consumes `GroupRestored` to clear the flag (reversible). Community-wide announcements are never affected by group soft-delete.

## Rich text & validation (14–16)
- **BR-14** — *(Revised 2026-08-07 — pivoted from server-sanitized HTML to Markdown.)* The body is authored and **stored as Markdown**, which is **inert at rest** — the server does NOT HTML-sanitize and carries no native sanitizer dependency (dropped `nh3`). Rendering to HTML happens at the **display boundary**: the SPA renders with `markdown-it` configured `html:false` (raw HTML disabled) and runs the output through **DOMPurify** before injection (SECURITY-05 stored-XSS defense at render). The server only length-bounds the stored Markdown. **Any non-browser consumer** (notably the Notifications email path reading `AnnouncementPublished.bodyPreview`) is responsible for its own render/escape — flagged for Unit 10. Rationale: avoids a native (`nh3`) Lambda dependency and its cross-platform wheel packaging, and keeps data inert at rest.
- **BR-15** — Consumed events (`EventCreated`, `GroupSoftDeleted`, `GroupRestored`) are processed **idempotently on the envelope id** via the standard idempotency table; redelivery never double-posts or double-hides.
- **BR-16** — All inputs are validated (type, length, format, enum) before processing; `title` is required and length-bounded; `target.groupIds` must be non-empty when `scope=groups`. Unimplemented contract operations return `501` (FQ8); all errors use the platform error shape with generic messages (SECURITY-15).

## Auto-post from events (17)
- **BR-17** — When Events publishes `EventCreated` with `announce == true`, Announcements auto-creates an announcement (authored by the event creator, targeted to the event's audience, `emailOptIn = announceByEmail`) via the standard create path (US-2.1). `announce == false` is a no-op. This is the same create logic as US-10.1, event-triggered rather than REST-triggered.
