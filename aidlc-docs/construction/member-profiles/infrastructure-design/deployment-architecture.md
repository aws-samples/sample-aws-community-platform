# Deployment Architecture — Unit 3: Member Profiles & Directory

**Stage**: CONSTRUCTION → Infrastructure Design · **Unit**: Member Profiles & Directory
Deploy-time composition and the mock→real transition for this service. Companion: `infrastructure-design.md`.

## Stack composition (Parameters, not exports — D1)
```
foundation.yaml ──outputs──▶ VpcId, PrivateSubnetIds, EventBusName, OpsAlarmTopicArn
api-edge.yaml ──outputs──▶ RestApiId, RootResourceId
   ├─▶ service-member-profiles-data.yaml ──outputs──▶ TableName, TableArn, StreamArn, IdempotencyTableName
   │        └─▶ service-member-profiles-app.yaml  (also receives EventBusName, RestApiId/RootResourceId,
   │                                                OpsAlarmTopicArn, EnableSemanticSearch)
root-template.yaml nests all of the above (unchanged composition pattern).
```
Route table for `/members` remains centralized in `api-edge.yaml` (generated by `infra/tools/gen_api_edge.py`); the `/admin/members` route is removed at Code Generation once the contract is amended (see `infrastructure-design.md` Q1) — this is the only route-table change for this unit; `/members` itself is unchanged (already Cognito-authorized, already proxying to `member-profiles-<stage>`).

## Mock → real transition (FQ7 — ordinary code deploy, same pattern as Identity & Access)
1. Real code lands in `services/member-profiles/src/` (`app.py` handler + `ProfileService`/`ActivityService`/`DirectoryQuery`/`FanOutClient`/`event_consumer` modules); `requirements.txt` pinned (smaller than Identity & Access's — no Cognito/SES/Secrets/CSV-import deps).
2. `-app` `Handler` changes `mock_handler.handler` → `app.handler`; new `AWS::Events::Rule` added for the 6-event subscription; scoped IAM policies replace the scaffold's broad `DynamoDBCrudPolicy` + add `execute-api:Invoke`.
3. Pipeline runs: build (vendored deps) → unit tests (incl. the degrade-path suite — simulated downstream 5xx/timeout per fan-out target, NFR-MP-MAINT-1) → **contract tests (gate, Schemathesis vs the frozen OpenAPI, post `/admin/members` removal)** → deploy `-data` (no changes — additive-only policy still holds even though nothing is added this time) → deploy `-app` → API `create-deployment` (only needed if the route table changed, i.e. once, for the `/admin/members` removal) → smoke test → `service-mode.json` member-profiles → `complete`.
4. Rollback = redeploy previous Lambda version (RESILIENCY-04). No data migration (same table, no schema change — this is the first real service so far that adds **zero** new persisted fields/indexes at this stage, since the profile-extension record's shape was already fully specified in Functional Design and needs no additive DDB attributes beyond what a schemaless DynamoDB item already supports).

## Availability & DR
- Multi-AZ via managed services (Lambda, DynamoDB, EventBridge) — RESILIENCY-08. This unit has no Cognito/SES dependency to factor into its own availability chain (its only hard dependency is the platform EventBridge bus + its own DynamoDB table; Contributions/Events/Forums/Certifications/Search are soft dependencies that degrade gracefully per BR-9).
- Backup & Restore DR (RESILIENCY-02/11): DynamoDB PITR + on-demand backups on the profile table. **Secondary recovery path unique to this unit**: because the profile-extension record is fully derived from Identity & Access's events, a table-level incident is, in principle, also recoverable by replaying Identity's event history (subject to EventBridge/archive retention) — documented as a secondary option, not a substitute for PITR/backups.

## Deploy-time seeding
None required. Unlike Identity & Access (which seeds a local-admin secret at deploy) or Settings (which seeds default config), Member Profiles' table starts empty and self-populates entirely from Identity & Access's `UserProvisioned` events as real users are provisioned — no custom resource or seed data needed for this service specifically. (The platform `seed.yaml` custom resource, which writes the bootstrap Administrator's Identity record, indirectly triggers this service's normal `UserProvisioned` consumption path — no special-casing required here.)

## Observability wiring
- Function logs (structured, correlation IDs) + standard error/latency/throttle alarms → `OpsAlarmTopicArn` (shared SNS topic, same as every other service).
- **Unit-specific additions**: fan-out failure-rate alarm (per downstream service — Contributions/Events/Forums/Certifications/Search) and event-consumer-lag alarm (`EventConsumerLagSeconds` p99 threshold) — both novel to this unit, reflecting its defining architectural pattern (read-time fan-out + event-sourced cache).
- X-Ray active tracing, with spans labeled per fan-out target so a trace visually shows which downstream call (if any) was slow or failed on a given request.
- Dashboard: `browseDirectory`/`getMember`/`getOwnProfile`/`memberActivity` p95 + error rate; fan-out failure count per downstream service; event-consumer lag trend.
