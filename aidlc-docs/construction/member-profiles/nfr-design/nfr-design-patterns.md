# NFR Design Patterns — Unit 3: Member Profiles & Directory

**Stage**: CONSTRUCTION → NFR Design · **Unit**: Member Profiles & Directory
How the NFR requirements are realized as concrete patterns in the service. Companion: `logical-components.md`. Plan: `../../plans/member-profiles-nfr-design-plan.md`.

## Resilience patterns (this unit's defining characteristic)
- **Parallel fan-out with per-call timeout (NFR-MP-PERF-2/3, RESILIENCY-10)**: `FanOutClient` issues all downstream calls for a single request (Contributions/Events/Forums/Certifications, and Search when semantic search is on) via `ThreadPoolExecutor.map`, each with an explicit `timeout≈300ms`. Every call is wrapped individually — a timeout, 5xx, or connection error returns `None`/empty for that call, never raises past the `FanOutClient` boundary. The calling domain service (`ProfileService`/`ActivityService`) merges whatever came back; missing sections are simply omitted from the response (BR-9), and the overall response is still `200`.
- **Per-container short-circuit, not a distributed circuit breaker (NFR-MP-SEC-6)**: after N consecutive failures to a given downstream service within one warm Lambda container, `FanOutClient` skips calling that service for a short cool-down window, returning empty immediately rather than re-waiting the full timeout on every request during a known outage. State is per-warm-container (resets on cold start) — an optimization to reduce wasted latency budget during an outage, not a correctness mechanism (the per-call try/except already guarantees correctness on its own).
- **Idempotent event consumption (NFR-MP-REL-3)**: identical mechanism to Identity & Access — `member-profiles-idem-<stage>` table keyed on `eventId` (TTL cleanup); each of the 6 consumed event types (`UserProvisioned`, `UserRoleChanged`, `UserDeactivated`, `UserReactivated`, `MemberJoinedGroup`, `MemberLeftGroup`/`MemberRemoved`) checks-then-writes the idempotency record before mutating the profile-extension record. Safe to redeliver/replay without corrupting state.
- **Graceful search degrade (BR-6b, D3)**: `DirectoryQuery` checks the cached `EnableSemanticSearch` flag; when on, `q` delegates to the Search service through the same `FanOutClient` pattern (still time-boxed — a slow/unavailable Search service falls back to keyword match rather than failing the directory request); when off, keyword match runs directly with no Search call attempted at all.
- **Recoverable-by-replay posture (NFR-MP-AVAIL-3)**: because the profile-extension record is entirely derived from Identity & Access's events plus the member's own profile-field edits, a partial/total table loss is a materially lower-severity incident than losing a canonical source-of-truth table — it can, in principle, be reconstructed from Identity's event history (subject to EventBridge/archive retention) plus re-prompting members for profile-only fields. This does not replace PITR/backups; it is a secondary recovery path documented for completeness.

## Performance patterns
- **Bounded total latency via parallelism**: the fan-out's total added latency is the slowest single call (≈300ms budget), not the sum of 4 sequential calls — this is the core mechanism behind the NFR-MP-PERF-1 targets (600ms profile reads, 1000ms leader activity summary).
- **No provisioned concurrency**: unlike Identity & Access's `login`/`verifyOtp`, no operation in this unit sits on an interactive auth-critical path; standard on-demand Lambda scaling is sufficient (NFR-MP-PERF-4).
- **Settings flag caching**: `EnableSemanticSearch` is read once per warm container with a short TTL rather than fetched from Settings on every `browseDirectory` call — avoids adding a 5th fan-out call to the request's own latency budget.

## Security patterns
- **Fail-closed in-service authZ (SECURITY-08)**: same `authz.py` convention module as Identity & Access — every handler builds a `Principal` from the Cognito-authorizer-validated JWT claims and calls `authorize()` against the shared permission matrix before touching data. `getMember`/`memberActivity` explicitly deny `Administrator` (BR-4); `memberActivity` additionally scopes `UserGroupLeader` to their own led group (BR-13) and denies `Member` entirely (self-view is `getOwnProfile`, not this endpoint).
- **Input validation (SECURITY-05)**: `validation.py` convention module (shared shape with Identity & Access, copied per-service per FQ1) validates free-text fields (`bio`, `skills`, `city`, `country`, `professionalRole`) for length caps and HTML/script rejection; query params (`q`, `role`, `groupId`, `certId`, `limit`, `cursor`, `from`, `to`) validated for type/format before use in any DynamoDB expression (parameterized, never string-built).
- **Least-privilege IAM (SECURITY-06)**: execution role scoped to this service's own table + idempotency table (DynamoDB CRUD), its EventBridge bus (PutEvents for `MemberProfileUpserted` + rule-based subscription to Identity's 6 events), and `execute-api:Invoke` scoped specifically to the Contributions/Events/Forums/Certifications/Search API Gateway resources it fans out to — read-only, no write actions on any other service's resources, no wildcards.
- **No credential surface (SECURITY-12 N/A)**: this service holds no secrets, no password/OTP logic, no Cognito admin calls — smallest attack surface of the services built so far, consistent with tech-stack-decisions.md's explicit "does NOT need" list.
- **Fan-out failure isolation (SECURITY-15)**: a failed downstream call is caught inside `FanOutClient` and logged with its own correlation ID + downstream-service tag; it is never allowed to propagate as a raw exception into the primary response — the platform's generic-error envelope applies only to primary-request-path failures, not to individually degraded fan-out sections.

## Observability patterns (RESILIENCY-05/07)
- **Three pillars**: Powertools structured logs + correlation IDs; X-Ray tracing spans API → Lambda → each fan-out call (labeled per downstream service) → (Search/OpenSearch when applicable); CloudWatch EMF metrics (`FanOutFailureCount` per downstream service, `FanOutLatencyMs` per downstream service, `EventConsumerLagSeconds` per event type, request error rate + p95 per operation).
- **Alarms**: elevated fan-out failure rate per downstream service (signals a dependency outage — informational for this service, since it degrades gracefully, but operationally significant); sustained event-consumer lag (p99 > 15 min) signaling a stuck consumer; standard error-rate/p95/throttle alarms per operation.
- **Health checks (RESILIENCY-06)**: shallow (process up) + deep (this service's own DynamoDB table reachability only — `describe_table`/sentinel `GetItem`). Deliberately does **not** deep-check Contributions/Events/Forums/Certifications/Search — those are expected-to-degrade dependencies, not requirements for this service's own health.

## Resiliency test scenarios (captured for Operations — RESILIENCY-14)
| Scenario | Expected behavior |
|---|---|
| Contributions/Events/Forums/Certifications 5xx or timeout | Affected fan-out section omitted from `getOwnProfile`/`getMember`/`memberActivity` response; overall response still `200`; `FanOutFailureCount` metric increments; alarm may fire if sustained |
| Search service unavailable, `EnableSemanticSearch` on | `browseDirectory` `q` falls back to keyword match; no user-facing error |
| Identity & Access event burst (e.g. after a large bulk import) | Consumer processes at EventBridge/Lambda default concurrency; some lag is acceptable (data stale, not wrong); `EventConsumerLagSeconds` rises and recovers as backlog drains |
| DynamoDB throttle (own table) | botocore backoff/retry within Lambda timeout; alarm on sustained throttles |
| Duplicate/redelivered Identity event | Idempotency table dedupes by `eventId`; no double-application, no corruption |
| This service's own Lambda cold start under load | No provisioned concurrency configured (not needed — non-interactive-critical path); standard scaling absorbs it within performance budget |
| Region/AZ event | Managed multi-AZ absorbs AZ loss; region loss → Backup & Restore runbook (inherited); profile table also secondarily reconstructable via Identity event replay (NFR-MP-AVAIL-3) |
